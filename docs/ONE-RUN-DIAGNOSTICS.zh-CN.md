# 同一轮游戏的卡顿诊断

v36 是基于 v35 行为的诊断版，不代表帧率或可玩性已经修好。游戏操作、退出和重新启动均由用户完成。代理不再为了追加测点要求逐次重开；诊断窗口可以在同一进程中再次开启。

## 覆盖

| 层次 | 证据 | 解释边界 |
|---|---|---|
| D3D12 请求与工作线程 | Execute、队列获取/排空、实际 Vulkan 提交与信号量等待、PSO 创建及原始结果 | Windows 的线程/进程编号不能直接当作 macOS 编号；对象关联必须有证据 |
| 资源与描述符 | descriptor copy 累计计数、采样耗时；原生 snapshot、缓存失效、只读计划、精确写声明、实际 Metal 调用 | 高频细项采用明确抽样，不能外推为完整耗时；按编码段汇总，避免逐资源 JSON |
| 编译与缓存 | 真实命中/未命中分支、配置序列化指纹、原生编译请求/回调、锁等待 | 代码 hash 不等于完整变体 key；闭源编译器内部仍不可见 |
| CPU 到 GPU | 逻辑提交、原生 command buffer 创建/提交/调度/完成、等待和事件值 | 不修改同步；缺失、分批和跨采样边界必须明确 |
| GPU 与呈现 | 有限时段的实际 GPU 时间戳及配对时钟；原生呈现时间戳 | 回调时刻不是实际呈现；时间戳差不是单条绘制独占耗时；不保证每条命令均被采到 |
| 主机和日志 | 进程/线程 CPU、前台连续区间、内存/交换/磁盘/温度限制、采集器成本、丢项和容量 | 全机压力不能全部归因于游戏；日志本身存在同步 I/O 成本 |

目前加载的 DXGI 二进制还没有匹配到精确、可重建的源码。因此，其内部限帧和帧延迟等待是明确缺口，只能由两侧计时及线程采样辅助判断。游戏和闭源驱动内部也没有完整可见性。这份覆盖不能证明一次测试会触发所有故障。

## 一轮采集

使用 `tools/capture_stutter_session.py`，指定已部署 profile 和独立输出目录；Windows sidecar 的两行路径须按原 Wine 实际 drive 映射配置。采集器预先挂好 marker，等待用户启动游戏，然后持续观察同一进程，定期或手动开启有限诊断窗口。它不会启动、关闭或控制游戏。

建议在同一轮中依次覆盖静止场景、移动/转视角、攻击、装备界面，记录动作先后。遇到卡顿先保留进程，让采集器继续抓取，不凭百分比或窗口是否还在就宣布成功。

原始 rolling 日志、CPU current/status、时钟、采样边界和覆盖损失单独保存。PID、启动时间、内核进程身份都须匹配；不能把旧进程日志混入本轮。磁盘或输出预算触顶时只关闭诊断，不终止游戏。

## 验证与限制

发布源代码前先验证 CPU 计数、并发、开关、轮转、尾事件、原始错误值，以及自有 GPU 输出。一次自有 GPU 测试已经发现并修正了新增日志错误：`getVkQueue()` 会重置 loader dispatch magic，日志必须使用纯读取身份函数。该错误没有部署给游戏。

同步日志仍有可测成本；分析时必须区分观察开销和游戏开销，不能把带日志的 FPS 当作无日志性能。探针通过不能替代游戏的正常画面、持续帧率、攻击/装备稳定性和 FSR3 超分/帧生成验证。现有下载仍为研究包。

## 同进程开销对照与后续代码准备

采集器现在支持 `--instrumentation-mode forensics-only`：只持有 `forensics.arm`，不请求 CPU 细项或 GPU 边界采样。它仍有观察开销，不能当成完全关闭日志的基线；不同场景/工作量之间也不能直接换算提速。滚动预算不足下一条完整 JSON 时会明确标记截断。

资源声明的下一步准备见 [独立 CPU 分类原型](../workspace/open-game-stack-20261015/evidence/sample-only-image-access-20261026/README.md)。原型拒绝未知或不安全的 image 操作；缺少真实语义验证器时也拒绝。它尚未接入 Native，不代表 heap、附件、生命周期、GPU 输出或帧率通过。

生产集成还需要访问资格升级、heap 准备后的精确读写例外，以及真实 GPU 回归。现有着色器序列化和缓存 UUID 尚未改变；新增源码不意味着已部署优化版。
